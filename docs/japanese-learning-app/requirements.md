# 日本語学習アプリ 要件定義書（ドラフト v0.1）

## 1. 背景と目的

- 対象ユーザー：スペイン語ネイティブの友人 1 名（JLPT N3 取得済み、N2 合格を目指している）
- 課題：
  - 漢字の **読み方** が難しい（特に熟語・音読み/訓読みの使い分け・特殊な読み）
  - 実際の会話（LINE）で、自分の返信が正しいか・自然かを確認する手段がない
- 目的：
  1. 日常の LINE 会話を教材にして「正しく・自然な日本語」を身につける
  2. 会話に出てきた漢字を中心に、読み方を反復練習できるようにする
  3. N2 合格に必要な漢字・語彙の読みを体系的にカバーする

> 補足：「N3 / N2」は **日本語能力試験（JLPT）** のレベル表記です（「日本語検定」は別の試験）。本書では JLPT N2 を目標として扱います。

## 2. 想定ユーザーと利用シーン

| 項目 | 内容 |
|---|---|
| 主ユーザー | スペイン語話者、JLPT N3、スマホ中心 |
| 説明言語 | スペイン語（切替で英語・やさしい日本語） |
| 主な利用シーン | ① LINE で返信した後に「今の返事、合ってた？」と確認 ② 返信する前に下書きをチェック ③ 通勤中などのスキマ時間に漢字の読み練習 |
| 利用端末 | スマートフォン（iOS / Android）。PC でも使えると尚可 |

## 3. 機能要件

優先度：**Must**（MVP に必須）／**Should**（早めに欲しい）／**Could**（余裕があれば）

### 3.1 LINE スクショ添削（コア機能）

| ID | 機能 | 優先度 | 内容 |
|---|---|---|---|
| F-01 | スクショ取り込み | Must | 画像を選択／カメラロールから複数枚アップロード。スマホの「共有」メニューからも受け取れる（PWA の Share Target） |
| F-02 | 会話の読み取り | Must | 画像から文字を読み取り、吹き出しの左右で **相手 / 自分** を判定して時系列の会話に復元。誤判定は手動で修正可能 |
| F-03 | 返信の正誤チェック | Must | 「自分」の発言ごとに 文法・語彙・表記（漢字/送り仮名）・助詞 の誤りを指摘 |
| F-04 | 自然さの提案 | Must | 「間違いではないが不自然」な表現に対し、より自然な言い方を 1〜3 案提示。なぜ自然かをスペイン語で説明 |
| F-05 | 文脈・相手との関係の考慮 | Must | 相手の発言内容に対して返信が噛み合っているかを判定。友達/目上など関係性（ユーザーが選択）に応じて **タメ口・丁寧語・敬語** のレベルが合っているか指摘 |
| F-06 | 相手の発言の解説 | Should | 相手のメッセージに含まれるスラング・若者言葉・略語（例：「りょ」「草」「それな」）、絵文字・スタンプのニュアンスを解説 |
| F-07 | 全文ふりがな表示 | Must | 会話内のすべての漢字にふりがなを付けて表示（ON/OFF 切替） |
| F-08 | 漢字・単語の抽出 | Must | 会話中の漢字語を抽出し、ワンタップで「読み練習リスト」に追加（N2 範囲の語は自動追加も可） |
| F-09 | 間違いノート | Should | 指摘された誤りを種類別（助詞・敬語・語彙…）に蓄積し、よくある間違いの傾向を表示 |
| F-10 | 返信下書きチェック | Should | 送信 **前** の返信文をテキストで入力 → 添削・自然な案を提示（スクショ不要の即時版。実際には事後より事前のほうが役に立つ場面が多い） |
| F-11 | 返信候補の提案 | Could | 相手のメッセージに対して、レベル別（シンプル／自然／丁寧）の返信例を提示 |
| F-12 | 読み上げ | Could | 会話文・修正案を音声で再生（TTS）し、読み方と発音を耳でも確認 |

**添削結果の出力イメージ**

```
あなた：「明日は行けるかどうか分からないです」
  判定：✅ 文法OK / 🔶 少し硬い
  自然な案：「明日行けるかまだ分かんない！」（友達向け）
  説明(ES)：Entre amigos, 「分かんない」 suena más natural que 「分からないです」...
  漢字：明日(あした) 行(い)ける 分(わ)かる → [練習リストに追加]
```

### 3.2 漢字の読み練習

| ID | 機能 | 優先度 | 内容 |
|---|---|---|---|
| K-01 | 読みクイズ（入力式） | Must | 漢字語を表示 → ひらがなで読みを入力（ローマ字入力→かな変換にも対応） |
| K-02 | 読みクイズ（選択式） | Must | 4 択。誤答選択肢は「ありがちな間違い」（長音・促音・濁音の有無、音訓の取り違え）から生成 |
| K-03 | 間隔反復（SRS） | Must | 正答率と回答時間に応じて次回出題日を自動調整（FSRS や SM-2 系のアルゴリズム） |
| K-04 | 出題ソース | Must | ① LINE 会話から抽出した語 ② JLPT N2 相当の漢字・語彙リスト ③ 自分で追加した語 |
| K-05 | 例文付き出題 | Should | 単語単体だけでなく例文の中で読ませる（文脈で読みが変わる語に対応：「今日」「一日」「上手」など） |
| K-06 | 苦手パターン練習 | Should | 間違えやすい読みをカテゴリ別に集中練習：連濁（人々・〜会社→がいしゃ）、促音化（学校・一緒）、長音（大きい／多い）、熟字訓（今朝・昨日・大人）、同じ漢字の複数読み（生：せい・しょう・い・う・なま） |
| K-07 | 漢字詳細カード | Should | 音読み・訓読み・意味（スペイン語）・部首・その漢字を使う N2 語彙・音声 |
| K-08 | 逆方向練習 | Could | 読み（かな）→ 正しい漢字を選ぶ（同音異義語：「機会／機械」「以外／意外」） |
| K-09 | 手書き入力 | Could | 書き取り練習（読みが主目的のため優先度は低い） |

### 3.3 学習管理・その他

| ID | 機能 | 優先度 | 内容 |
|---|---|---|---|
| L-01 | 進捗ダッシュボード | Should | 覚えた漢字数／N2 漢字リストのカバー率、連続学習日数、添削回数 |
| L-02 | 今日の復習通知 | Should | 復習期限の語がある日にプッシュ通知（PWA の Web Push） |
| L-03 | N2 文法の紐付け | Could | 添削で出た文法事項（〜わけではない、〜っぽい 等）を N2 文法項目と紐付けて解説 |
| L-04 | 模試モード | Could | JLPT N2「漢字読み」形式の問題を時間制限付きで解く |
| L-05 | データのエクスポート | Could | 単語リストを CSV / Anki 形式で書き出し |

## 4. 非機能要件

### 4.1 プライバシー・セキュリティ（重要）

LINE のスクショには **第三者（会話相手）の名前・アイコン・メッセージ** が含まれるため、最も配慮が必要な領域です。

- 画像は解析後すぐ破棄し、サーバーに保存しない（保存するのはテキスト化した会話と添削結果のみ。これもユーザーが削除可能）
- 解析前に、名前・アイコン部分を塗りつぶせる「マスク機能」を用意（Should）
- 会話相手の名前は保存時に「相手A」などに置換するオプション
- AI の API キーはサーバー側（サーバーレス関数）でのみ保持し、ブラウザに露出させない
- 利用は本人のみ（ログイン必須）。不特定多数への公開はしない

### 4.2 品質

- **ふりがなの正確性**：LLM 単体は読みを間違えることがあるため、形態素解析＋辞書（後述）で読みを付け、LLM は添削・説明に専念させる二段構えにする
- 添削の確信度が低い場合は「どちらも可」「文脈次第」と正直に表示し、断定しすぎない
- 説明は学習者向けに簡潔に（1 指摘あたり 2〜3 文程度）

### 4.3 性能・コスト

- スクショ 1 枚の解析〜結果表示：15 秒以内を目標（解析中は進捗表示）
- 漢字クイズはオフラインでも動作（出題データと学習履歴は端末にキャッシュ）
- AI API の利用料が主なランニングコスト。1 日あたりの解析回数に上限を設定できるようにする

### 4.4 UI / UX

- スマホファースト、片手操作
- UI 言語：スペイン語／日本語切替
- ダークモード対応

## 5. 基本設計

### 5.1 全体構成

```
[スマホ (PWA)]
  ├─ スクショ添削画面 ──画像──▶ [サーバーレス API]
  │                              ├─ ① Vision 対応 LLM：画像→会話テキスト(JSON)
  │                              ├─ ② 形態素解析＋辞書：ふりがな・単語分割
  │                              └─ ③ LLM：添削・自然な案・解説(JSON)
  ├─ 漢字練習画面（SRS はクライアント側で計算、オフライン可）
  └─ 学習データ同期 ◀────────▶ [データベース]
```

### 5.2 技術スタック案

| レイヤー | 候補 | 理由 |
|---|---|---|
| フロントエンド | React（Next.js または Vite）＋ PWA | ホーム画面に追加でアプリのように使える。ストア申請不要で、まず 1 人に配るのに最適 |
| API | Cloudflare Workers / Vercel Functions | API キーを隠せる。小規模なら無料枠でほぼ収まる |
| AI | Vision 対応 LLM（例：Claude） | スクショの読み取り（吹き出しの左右判定込み）と添削を同じモデルで処理できる。出力は JSON スキーマで固定 |
| ふりがな | 形態素解析（Sudachi / kuromoji.js 等） | 読みの正確さを担保 |
| 辞書データ | KANJIDIC2・JMdict（EDRDG、CC BY-SA） | 漢字の音訓・意味（英語。スペイン語訳は一部収録／LLM で補完） |
| DB・認証 | Supabase または Firebase | 認証・DB・ストレージが一体。個人利用なら無料枠 |
| TTS | ブラウザ標準の Web Speech API（初期）→ 必要ならクラウド TTS | 初期コストゼロ |

> 注：このリポジトリの GitHub Pages は静的ホスティングのみのため、API キーを扱う処理は置けません。フロントだけ GitHub Pages に置き、API は別のサーバーレス環境に置く構成になります。

### 5.3 主要データモデル

| エンティティ | 主な項目 |
|---|---|
| User | id, 母語, 目標レベル, 説明言語 |
| Conversation | id, user_id, 相手との関係（友達/先輩/先生…）, 作成日時 |
| Message | id, conversation_id, speaker（self / other）, text, 順序 |
| Feedback | message_id, 判定（OK/要修正/不自然）, 指摘リスト, 自然な案, 説明 |
| Vocab | id, 表記, 読み, 意味(ES), JLPT レベル, 出典（LINE/N2リスト/手動） |
| ReviewCard | user_id, vocab_id, 次回出題日, 安定度, 難易度, 正答/誤答回数 |
| Mistake | user_id, カテゴリ（助詞/敬語/語彙/表記…）, 元の文, 修正文, 日時 |

### 5.4 スクショ添削の処理フロー

1. 画像アップロード（任意で名前・アイコンをマスク）
2. LLM（Vision）で会話を抽出 → `[{speaker, text, time}]` の JSON
3. ユーザーが抽出結果を確認・修正（話者の取り違えなど）
4. 相手との関係を選択（初回のみ、会話ごとに記憶）
5. 形態素解析でふりがな・単語を付与
6. LLM で「自分」の各発言を添削 → 判定・指摘・自然な案・スペイン語説明の JSON
7. 結果表示 → 漢字語を練習リストへ追加、誤りを間違いノートへ保存
8. 画像は破棄

## 6. 開発フェーズ（案）

| フェーズ | 内容 | 目安 |
|---|---|---|
| Phase 0：検証 | 実際の LINE スクショ数枚で、LLM の読み取り精度と添削品質をプロンプトだけで確認 | 数日 |
| Phase 1：MVP | F-01〜F-05, F-07, F-08 / K-01〜K-04 / ログイン | 2〜4 週間 |
| Phase 2 | 返信下書きチェック(F-10)、間違いノート(F-09)、苦手パターン練習(K-06)、進捗・通知 | +2〜3 週間 |
| Phase 3 | スラング解説、読み上げ、N2 文法紐付け、模試モード | 以降随時 |

まずは Phase 0 で「本人に実際のスクショで使ってもらい、添削が役に立つか」を確かめるのが一番の近道です。

## 7. 未決事項（本人・作り手で決めたいこと）

1. 説明はスペイン語のみでよいか、日本語併記がよいか（N2 を目指すなら「やさしい日本語」併記も学習効果あり）
2. 添削の厳しさ：細かい表記ゆれまで指摘するか、伝わるかどうかを重視するか（設定で切替も可）
3. 会話相手のプライバシー：相手に「学習に使っている」ことを伝えるか、マスク機能を必須にするか
4. 運用コストの負担者と上限（AI API 利用料）
5. 配布方法：PWA で十分か、将来的にストアアプリにするか
6. 学習履歴を端末内だけに置くか、クラウド同期するか（機種変更時の引き継ぎ）
